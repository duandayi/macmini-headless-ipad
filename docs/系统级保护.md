# 系统级保护：让这些组件「不能被改」

2026-10-27 那次事故的教训：**登录项被某个程序清空，整套连接直接失效，而且没有任何提示**。
所以本项目除了「能连」，还要保证「连的能力不会被悄悄破坏」。

## 三层锁

| 层 | 机制 | 挡住谁 |
|---|---|---|
| 1 | 主副本 `schg`（系统级不可变）+ `root:wheel` | 连 **root** 都要先 `chflags noschg` 才能改 |
| 2 | 用户侧副本 `uchg`（用户级不可变） | 普通程序写入直接 `Operation not permitted` |
| 3 | root 守护 `com.dsh.sidecar-protect` 每 **20 秒**巡检 | 文件被还原、LaunchAgent 被卸载会重新加载、进程被杀会 kickstart |

## 实测（2026-10-28）

| 攻击方式 | 结果 |
|---|---|
| 用户权限 `echo x >> vdisplay` | `Operation not permitted` |
| 管理员权限写主副本 | `Operation not permitted`（schg） |
| `launchctl bootout` 掉菜单栏 agent | 约 40 秒后自动重新加载 |
| 先解锁再改用户侧文件 | **15 秒**后被还原并重新上锁 |

## 诚实的边界

- **拿到管理员密码的人是能改的**（先 `chflags noschg`）。这是 macOS 的权限模型上限，任何软件都一样。
- 如果 root 守护自己（`com.dsh.sidecar-protect`）被删，保护链就断了。所以它也被 `schg` 锁住。
- 保护的是**文件与启动项**，不是"进程永远不会崩"——崩了有 KeepAlive 和巡检兜底。

## 更新组件时的正确顺序

```bash
# 1) 解锁
sudo chflags noschg /usr/local/libexec/dsh-sidecar/*
sudo chflags nouchg ~/.local/bin/vdisplay
# 2) 改 /tmp 里的副本并测试
# 3) 覆盖主副本（先！）再同步用户侧
sudo install -o root -g wheel -m 755 /tmp/vdisplay /usr/local/libexec/dsh-sidecar/vdisplay
sudo install -o $USER -g staff -m 755 /usr/local/libexec/dsh-sidecar/vdisplay ~/.local/bin/vdisplay
# 4) 重新上锁
sudo chflags schg /usr/local/libexec/dsh-sidecar/*
sudo chflags uchg ~/.local/bin/vdisplay
```

> 只改用户侧会被主副本在 20 秒内盖回去（这是保护在工作，不是 bug）。
